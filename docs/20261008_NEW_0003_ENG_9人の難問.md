# 9人の難問（推論エンジンを容疑者9人まで広げる）

- 管理番号: #0003
- 種類: NEW（新機能）
- 対象: 推論エンジン（ENG）と、その検査 `tools/check-engine.mjs`
- 作成日: 2026-10-08
- 関連: #0001（現状の仕様と構成。4章のエンジン・11章の制限）、#0002（VERSION 3 になった修正）。画面側の対応（9人の問題を Web Worker で作る・難問の入口）は別の文書に書く

## 概要

推論エンジンが作れる問題を、容疑者3〜6人から **3〜9人** に広げた。7〜9人は「難問」として★3に固定し、9人でも「答えが1つ」「仮定の入れ子なしで、人が順に考えれば解ける」「解説が長すぎない」問題だけを出す。**3〜6人の問題（日替わり・練習）は1文字も変わらない**ので、エンジンの `VERSION` は 3 のまま上げていない。あわせて、エンジンが Web Worker の中でも動くようにし、検査に 7〜9人の項目と「3〜6人の問題が変わっていないか」の回帰テストを足した。

## 対象ファイル

- `index.html` の推論エンジン（`// ==ENGINE START==` 〜 `// ==ENGINE END==` の間）
  - 開発は共有フォルダの外の作業用ファイルで行い、仕上がった中身を ENGINE START〜END の間にそっくり入れ替える（画面側の作業と合わせて組み込む）。作業用ファイルはこのフォルダに置いていない
- `tools/check-engine.mjs`（検査の追加。約50KB）

## 変更内容

### 1. 全世界の表を9人まで持てるようにした（`ctxFor` / `computeHS` / `evalC`）

- 「世界」＝（だれが正直者か × だれが犯人か）。9人では 2^9 × 9 = **4,608 通り**（6人は384通り）
- これまでは、犯人ごとに 2^N ビットを 32bit の語 1〜2個（6人まで）で持っていた。これを語 K 個の配列にした（5人以下 K=1、6人 2、7人 4、8人 8、9人 16）
- 事実に合う世界の集合（`computeHS`）と、1つの証言から決まることの取り出し（`evalC`）を、K 語をループで回す形にした。中身の計算（ビットの AND / OR）は同じなので、6人以下の結果は変わらない
- 表のキャッシュのキーを「話し手の番号 ×8」から「×16」にした（9人目の番号 8 が別の証言と重ならないように）

### 2. 人数の範囲と★（`normOpts`）

| 指定 | これまで | これから |
|---|---|---|
| `people` | 3〜6 に丸める（7 以上は 6人） | **3〜9** に丸める（10 以上は 9人） |
| `star`（7人以上） | — | 何を渡しても **★3**（難問）。`targetStar` も 3 |
| `band`（7人以上・省略時） | — | `'hard'`（下の3） |

6人以下の丸め方・★・band の決め方は今までどおり。

### 3. 7〜9人の作り方（`HARD` / `hardOk` / band `'hard'`）

7人以上のときだけ、次の表の値で作る。6人以下は使わない（`buildCandidate` / `buildCore` に7人以上のときだけ `hard` を渡す。6人以下は今までとまったく同じ手順・同じ乱数の使い方）。

| 項目 | 7人 | 8人 | 9人 | 意味 |
|---|---|---|---|---|
| 仮定の回数 | 2〜3 | 2〜4 | 2〜4 | 上限を超える候補は捨てる（`hypsMax`）。2回未満は band 'hard' の外 |
| 仮定の手の合計 | 7以上 | 7以上 | 8以上 | band 'hard' の条件（`sumMin`）。6人★3（日曜）の「7以上か連鎖5以上」より重め |
| 連鎖の上限 | 10 | 11 | 12 | 1つの仮定の中の手＋矛盾の1手（`chainMax`。6人以下は今までどおり10） |
| 解説の行数の上限 | 22 | 24 | 26 | 画面の解説で並ぶ行数（仮定は見出し・中の手・矛盾・結論を1行ずつ）。超える候補は捨てる（`lines`） |
| 証言の種類の数 | 4以上 | 5以上 | 5以上 | 少ない候補は捨てる（`minTypes`） |
| 同じ種類の証言 | 2個まで | 3個まで | 3個まで | 証言を選ぶ段階で、上限に達した種類を選ばない（`typeCap`） |
| 候補を作る回数の上限 | 600 | 600 | 600 | 6人以下は今までどおり1,500（`attempts`） |
| 解を1つにする山登り | 60回 | 70回 | 80回 | 6人以下は今までどおり50回（`climb`） |

- 守ること（6人以下と同じ）: 解が1つ（総当たり）／仮定の中で別の仮定・場合分けをしない（入れ子なし）／「犯人は嘘つきだ」の自己言及のひっかけを直接の推論に使わない／解説に使われない証言は最大1つ（最初の4割の試行は0個だけ）／「わたしとX」と「正直者の人数」は1問に1つまで
- 「仮定の回数」「解説の行数」「種類の数」を外れた候補は、合格が見つからないときの「いちばん近いもの」にも使わない。実際には9人で平均11回・最大89回（1,000問）の試行で合格が出ていて、上限600回に届いた問題は無い
- 生成は試行の回数だけで止める（時間では止めない）。時間で止めると、端末の速さで問題が変わってしまうため

### 4. 村人の色

色は今までどおり8色（`color` は 0〜7）。9人のときだけ、カードの0番と8番（最初と最後）が同じ色になる。画面は変えなくても表示できる。

（#0007 で画面側に9色目 `--p8` を足し、9人目が他の人と同じ色なら画面で9色目に置き換えるようにした。エンジンの `color` は 0〜7 のまま変えていないので、問題も `VERSION` も変わらない）

### 5. Web Worker の中でも動く

- エンジンは DOM・`window`・`localStorage` を使わない（もともと使っていない）
- 最後の行で、`window` があれば `window.Engine`、無ければ `self.Engine` に入れる（Worker の中は `self`）。Node では `module.exports`
- 画面側は、ENGINE START〜END の中身に「メッセージを受けて `Engine.generate` を呼ぶ」数行を足して Worker を作れる（`Engine` でも `self.Engine` でも呼べる）

### 6. 公開 API

- **変えていない**: `generate({seed, people, star, band?})`、`daily`、`dailyConfig`、`check`、`hint`、`solve`、`example`、`localDateStr`、`addDays`、`VERSION`（3 のまま）、`TYPES`。9人は `Engine.generate({ seed, people: 9, star: 3 })` で作る
- **足したもの**: `Engine.LIMITS = { minPeople: 3, maxPeople: 9, hardFrom: 7, hardStar: 3 }`（凍結済み）。画面はこれで「9人に対応したエンジンか」「何人から難問か」を見分けられる
- `_internal.BANDS`（名前の一覧）に `'hard'` が増えた
- 動きが変わる点: `people` に 7〜9 を渡すと、これまでは6人の問題だったのが、その人数の難問になる（画面の練習は4〜6人しか渡していないので影響なし）
- 日替わり（曜日の表）は変えていない。日替わりに7人以上は出ない

### 7. 検査（`tools/check-engine.mjs`）に足したもの

| 項目 | 内容 |
|---|---|
| 回帰（3〜6人） | 日替わり 2026-10-01 から365日分と、練習240問（★1〜3 × 3〜6人 × seed 'r0'〜'r19'）の JSON の SHA-256 を、VERSION ごとの基準値（`GOLDEN`）として持つ。違えば FAIL にし、「3〜6人の問題が変わりました。意図した変更なら VERSION を上げて docs に書き、GOLDEN に新しい値を足す」と表示する。VERSION を上げたのに基準値が無いときも FAIL にし、足す値を表示する |
| 7〜9人の問題 | 人数ごと100問（`--count-hard` で変更可）。これまでの全項目（総当たりでの一意性、解説の各手順の検算、仮定の矛盾が本物か、入れ子なし、文章、`check`、`hint` など）を9人まで同じように行う |
| 7〜9人の決まり | ★3、仮定の回数と手の合計、連鎖の上限、解説の行数・文字数（7人1,300字・8人1,400字・9人1,500字まで）、種類の数・同じ種類の数・「正直者の人数」は1つまで、全体で1つの種類が25%を超えない・全11種類が出る、使われない証言がある問題は10%以下 |
| 7〜9人の API | ★を何で指定しても★3、人数は3〜9に丸める、`Engine.LIMITS` |
| 7〜9人の速さ | 人数ごとに平均150ms以下・最大1.5秒以下（Node） |
| Worker | `window`・`document`・`module` の無い環境（`self` だけ）で読み、`self.Engine` で同じ問題を作れる・`hint`・`check` も動く |

- 総当たりの全世界の一覧をキャッシュして、9人の検査を速くした
- 3〜6人の速さの検査（平均30ms・最大300ms）は3〜6人だけで測るようにした

## 3〜6人の問題が変わらないことの確かめ方と結果

1. 変更前のエンジン（`index.html` の ENGINE START〜END をそのまま取り出したもの）と変更後のエンジンを、別々に読み込んで同じ入力を渡し、`JSON.stringify` の結果を1件ずつ比べた（比較用のスクリプトは作業用フォルダに置き、このフォルダには残していない）

   | 比べたもの | 件数 |
   |---|---|
   | 日替わり `daily` と `dailyConfig`（2026-10-01〜2036-09-27 の 3,650日） | 7,300 |
   | 練習 `generate`（★1〜3 × 3〜6人 × seed 500個 × 数と画面と同じ形の文字列 `'p…'` の2種類） | 12,000 |
   | band を指定した `generate`（9種類 × ★ × 人数 × 5） | 540 |
   | 範囲外・型違いの入力（人数 0・2・'5'・4.7、★0・9、null など） | 8 |
   | `solve` / `check` / `hint`（上の問題から339問を選び、誤答4通りと途中の印4通りで） | 4,407 |
   | `example`・`addDays`（2件）・`VERSION`・`TYPES` | 5 |
   | 合計 | **24,260件、違い 0件**（全体のハッシュも一致） |

2. 同じ結果を検査に回帰テストとして入れた（上の7）。基準値は変更前のエンジンで作り、変更後のエンジンでも同じ値になることを確かめた
   - 日替わり365日: `964b8ed41145a3cc4878e1c4afa8533e`
   - 練習240問: `fe126bada59957334b67c3251b261039`
3. 問題が変わらないので、**`VERSION` は 3 のまま**。解きかけの記録もそのまま使える

### 9人の問題を自分で解いてみた

9人の問題を2問、解説を見ずに解き、どちらもエンジンの答えと一致した。入口（村長のメモや「わたしとXは同じ側」）から一本道で進み、詰まったところは「この人が正直者なら？」と1人だけ仮に決めれば矛盾まで届く。理不尽な飛躍は無かった（1問 5〜10分ほど）。

例: `Engine.generate({ seed: '9nin-1', people: 9, star: 3 })`「半分になったパイ」（★3・仮定3回・解説24行）

> 村長のメモ：モモは正直者だ
>
> モモ「ミオとシノのうち、少なくとも1人は嘘つきなのよ」／ナギ「シノは嘘つきさ」／リツ「わたしも入れて数えると、正直者はちょうど2人だ」／オト「やったのはウタだぜ」／ミオ「やったのはオトだ」／シノ「オトかウタ、どちらかが犯人よ」／エマ「リツとウタは違う側なんだ」／ウタ「ミオは正直者よ」／レン「ナギとミオは、2人とも正直者か、2人とも嘘つきだぞ」

考える順番（解説の流れ）: リツが正直者だと正直者は2人だけになりナギの証言と食い違う → リツは嘘つき。ミオが正直者だと犯人はオトでシノの証言と食い違う → ミオは嘘つき（ウタ・エマも嘘つき）。ナギが正直者だと、人数の条件からレンが正直者になりレンの証言と食い違う → ナギは嘘つき。あとは一本道で、正直者はモモ・オト・シノ・レン、犯人はウタ。

もう1問（`seed: '9nin-a'`「消えた虫めがね」、メモなし・仮定4回・解説26行）は、ハルの「わたしとレンは同じ側」からレン・シノが決まり、シノの「正直者はちょうど5人」を使って解く問題だった。

## 画面側への注意（9人の問題を Worker で作る担当へ）

- 9人の問題は `Engine.generate({ seed, people: 9, star: 3 })`。戻り値の形は今までと同じ（`people: 9`、村人・証言が9件）。7〜9人は `star` に何を渡しても★3
- 9人に対応したエンジンかどうかは `Engine.LIMITS && Engine.LIMITS.maxPeople >= 9` で分かる
- Worker の中では `Engine` も `self.Engine` も使える。DOM は使わない。Worker が使えない環境では、メインスレッドで同じ関数を呼べば同じ問題になる
- 9人のときは `villagers[0]` と `villagers[8]` の `color` が同じ（色は8色のまま）。似顔絵・名前は別
- 練習の途中を保存して開き直すときは、seed・人数・★が同じなら同じ問題になる（9人も同じ）
- `check` / `hint` / `solve` は9人の問題でもそのまま使える（`hint` は問題に入っている解説を使うので速い）

## index.html への組み込み（統合。2026-10-08）

- 作業用のエンジンの中身を `index.html` の ENGINE START〜END の間にそっくり入れ替えた。入れ替えた後の中身は作業用のものと1文字も違わない（diff で確認）。目印の行は `// ==ENGINE START==` が867行目、`// ==ENGINE END==` が2287行目（PWA のタグなどを足した後の位置）
- `node tools/check-engine.mjs index.html`: **全64項目 PASS（約9秒）**。回帰の2項目（日替わり365日・練習240問）も PASS したので、3〜6人の問題は変わっていない。`VERSION` は 3 のまま
- 7〜9人の生成時間（Node、`index.html` から取り出したエンジン、各100問）: 7人 平均2.0ms・8人 2.5ms・9人 5.4ms、最大22ms
- ブラウザ（http://127.0.0.1:8793/ 、375px）: 難問カードの「準備中」が消え、押すと Web Worker で9人の問題ができた（Worker の準備 16〜58ms、問題が届くまで 39〜84ms）
- 9人の問題を1問、解説を見ずに解いた: 「消えたいちごジャム」（村長のメモなし・仮定2回・手順10）。リツ「イツキは正直者だ」からイツキとリツは同じ側、シノ「イツキとリツが2人とも正直者ってことはない」からシノはイツキの逆…と人どうしの関係をつなげると、オトの証言が必ずウソになり、そこから一本道で決まる。答え（正直者 エマ・シノ・アオイ、犯人 イツキ）は解説と一致し、理不尽な飛躍は無かった。ヒント（2段）と、誤答の食い違いの説明も9人で正しく出た
- 村人の色（4章）は8色のまま入れた。9人のときは1人目と9人目が同じ色になる（確かめた2問でも「サクとオト」「カイとスズ」が同じ色）。名前と似顔絵で見分けられるので、今回は変えていない。9色にするなら、画面に `--p8`（ライト・ダークの両方）を足し、エンジンの色の割り当て（`colors[i % 8]`）と検査の「color は0〜7」を直す。変わるのは9人の問題の色だけなので `VERSION` は上げなくてよい
  - → #0007 で、エンジンは変えずに画面側だけで9色目（`--p8`）を使う形にした
